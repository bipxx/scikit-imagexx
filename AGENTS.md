# Applying these instructions

- At task entry and before editing a new area, read the applicable `AGENTS.md` instructions, including any more specific instructions in that area. Treat them as execution requirements; resolve conflicts using instruction priority and the user's current scope.
- Put the relevant requirements into the existing task's acceptance criteria and handoff. When delegating, give the worker its file ownership, applicable rules and required evidence; require its closeout to identify any unmet requirement. Do not create a second checklist or reporting system.
- Before a dependent action, verify its actual prerequisites from source, retained evidence and live handles. If a rule was missed or a required check failed, stop dependent actions, correct the affected work and rerun only invalidated checks. Preserve the failure and explain any material effect to the user; do not silently waive a requirement or claim completion.
- Before commit, merge, push or task closeout, check the applicable requirements against the actual diff and evidence. Report the concrete result, validation and remaining gates. Documentation-only tasks require document checks; they do not authorize implementation or expensive scientific reruns.
- Enforce these rules in the existing task record: before execution, identify the applicable acceptance gates, responsible owner and evidence required for the next dependent action. At handoff or closeout, mark each applicable gate passed, pending or failed with its source/receipt or concrete reason. A plan entry, queued message, partial test run or author assertion is not evidence that its gate passed. Proceed with a dependent action only after every mandatory prerequisite for that action has passed within its required source/runtime scope; missing, stale or unverified evidence leaves the gate pending. Keep this proportional to the task; do not copy this file into every handoff.
- At each action boundary, enforce the applicable gate against the actual result: inspect the command exit status and required receipt before starting a dependent mutation or dispatch. A shell continuing after an error does not establish success. Never replace a required complete check with a smaller proxy or change its acceptance criteria merely to pass. Once all prerequisites pass, proceed with the authorized next action promptly; do not add another review layer or repeat unchanged validation.
- If a requirement is missed, stop only actions that depend on it; preserve useful independent work and valid evidence. Record the missed requirement, its material effect and the narrow correction in the existing checkpoint before resuming dependent work. Do not silently weaken a gate, substitute different checks, or report an in-progress job as passed. The delegating agent remains responsible for verifying the worker handoff against these requirements before integration or acceptance; a worker completion message does not waive an unmet gate. Resolve conflicting instructions by priority and scope; report any gate that remains unmet. Routine authorized work does not require a new user approval; ask only when an applicable instruction or a material scope decision requires it.

# Repository workflow

- Merge and push validated, reviewable increments back to `main` promptly; do not accumulate completed feature work in worktrees.
- After merging, remove obsolete worktrees with `git worktree remove`, first checking that their tracked and untracked source changes are clean and their commits are ancestors of `main`.
- Keep build outputs in ignored build directories. Remove obsolete build caches after verification; retain active environments, running-job files, reproducible baseline packages, raw benchmark results, and unfinished source work.
- Resolve and check cleanup paths against this workspace before recursive deletion. Never delete the entire `build/` directory: it also holds active worktrees.
- Keep performance measurements isolated from builds and tests. Do not remove or rebuild files used by a running benchmark.
- For Windows-linked worktrees, use native Windows Git. When a WSL task needs Git, verify that command and its explicit Linux environment at the actual entry point before frozen reference, qualification or measurement dispatch; reuse this evidence while the environment/worktree is unchanged. Private iterative tests may use dirty source authenticated by exact bytes and absolute commands; do not impose clean-HEAD or repeated Git checks on every private test process. Reuse the working launcher, without changing repository format or worktree metadata to bridge shells.

# Execution discipline and throughput

- Use `coverage/EXECUTION_PLAN.md` for the current sequence and `coverage/work_items.json` for operational state. Reconcile them with actual source, receipts and live handles at transitions. Historical assignments are evidence, not dispatch orders. Correct stale next gates instead of creating another queue or tracking framework.
- Honor an explicit implementation pause. Documentation or planning requests do not resume agents, builds, numerical tests or benchmarks; resume implementation only when the user authorizes it.
- During implementation, use three independent workers when dependency-ready work exists. Assign each a coherent API batch and exclusive family-specific files, including its native code, hot-swap parity, installed SDK and benchmark coverage. Root reserves shared registry/build/workflow files and assigns one integration author at a time; root retains independent admission and main delivery. Workers must preserve others' edits. Do not split a small operation into serial administrative handoffs or invent work to fill a lane.
- Limit each worker to one implementation and one frozen handoff; keep at most one ready cumulative release candidate. Reuse existing reviewed components, primitives, fixtures and benchmark infrastructure before adding code. Freeze the earliest compatible ready bundle without waiting for unfinished lanes; complete independent admission and required release gates, then merge/push promptly.
- Before repeating a check, build, download or measurement, name its changed input or unresolved failure. Documentation needs relevant link/format/state checks. Reuse passing evidence only within its established source/runtime/profile scope; rerun affected checks after a fix, expanding when the dependency closure requires it. Never rerun an unchanged performance experiment for favorable results or to refresh bookkeeping.
- Prevent redundant automatic CI for validated documentation/receipt-only increments that change no executable inputs: use `[skip ci]` after the relevant document checks pass. Also mark private candidate commits when their required validation will run through explicitly dispatched workflows. This avoids duplicate automatic campaigns; it does not waive affected source tests, genuine preparation, parity, benchmarks or release qualification.
- Before real dispatch, verify scratch capacity, actual retained manifest fields, workflow selectors/collector boundaries and source identity using existing setup checks. Inspect retained results first. Fix demonstrated setup failures before dependent work; do not add another preflight framework or repeat expensive authentication of unchanged retained archives.
- Every advertised function requires contract parity and relevant one-thread public-call performance evidence against original scikit-image. Verify hot-swap behavior, installed native ownership, applicable scalar/SIMD paths and optional process-global workers with default1. Disclose provider computation, ordered serial cores, unsupported domains and slower cases. Minimum preparation, source checks and a root reconstruction do not replace independent admission or exact-source four-profile release qualification.
- Measure progress by reviewed API/domain closure and delivered increments. Packet counts, assertion counts and partial registrations do not establish full parity or library-wide speed superiority. Preserve failed experiments and prospective gates; optimize a demonstrated bottleneck rather than an unverified explanation.

# Task closeout and waste review

- After each bounded task reaches a terminal outcome, record result/evidence, avoidable work and reuse, and the next-plan correction with owner/trigger (or "reviewed, no change") in its existing handoff/checkpoint. Distinguish useful rejected experiments from preventable setup or duplicate work. Use observed costs when available; do not rerun work merely to measure waste.
- Before the next dependent task, update the affected action in `coverage/EXECUTION_PLAN.md` and existing operational task fields when the review changes execution. Include material process corrections in the validated increment; preserve historical evidence and use existing records rather than adding a reporting framework.

- At a task transition, reconcile actual agent/job status and evidence before dispatch. Use `followup_task` for every request to execute or continue work, including when the agent may still be running; reserve `send_message` for context only. Confirm a live resumed handle before depending on progress; a queued message alone does not start work. Retire terminal dispatch instructions when updating the next gate.

- Closeout is part of the task, not a separate audit project. Update its existing next gate with the terminal outcome, exact source/receipt, reusable and still-pending evidence, and next owner/trigger. Derive reported counts from retained results; leave unknown costs explicit. If the review finds no change, record "reviewed, no change" and continue without an extra task, scientific rerun or standalone documentation commit.

- Finalize receipt paths, labels and closeout before handing off a hash. Handed-off bytes are immutable; corrections require a versioned successor with the predecessor retained. Review only the affected metadata delta and do not replay unchanged scientific evidence.
- Inspect branch ancestry before merging a reference packet into main. If it descends from unfinished integration work, restore only its independently reviewed files after confirming their dependencies are already present; do not import the private implementation accidentally. A failed merge or check must stop dependent mutations. Commit only after conflict markers and index checks pass; verify the final shipping source projection against the validated candidate, especially after a reverted merge.

- Before hosted preparation, run changed source-only benchmark/metadata guards on both retained supported Python versions; source-plan commands do not execute those guards. For new cross-version code-immutability checks, compare pinned source bytes or parse the baseline and candidate on the same interpreter. Frozen AST dumps include interpreter schema and must not be treated as portable source hashes. Preserve historical pins and failures.
- Before hosted release qualification, require a passing execution of the complete workflow source-check command on both retained supported Python versions, with the actual selectors and normal conftest/plugins enabled. Collection audits, unions of partial runs and checks with altered configuration do not satisfy this gate. Run the complete barrier without fail-fast so all failures are visible; after fixing them, rerun the complete affected barrier before dispatch.
- Evidence reuse requires matching dependency scope, including literal file/hash assertions, selector lists and test configuration. A metadata-only change that preserves production code can preserve numerical and benchmark evidence while invalidating source guards. If a readiness claim proves wrong, explicitly supersede it, retain the failed campaign and fix the missed dependency before a successor dispatch; never retry unchanged source or relabel the earlier gate as passed.

- Once required readiness and the affected next gate are closed, dispatch eligible hosted work promptly; batch unrelated publication, broad ledger refresh and next-family reviews while it runs. A single explicitly assigned owner may author shared integration in an isolated candidate; root retains independent admission and main delivery.

# Engineering judgment and simplicity

- Match defensive complexity to a concrete risk. Address ordinary correctness issues and realistic concurrency or security risks within the agreed scope. Before adding substantial machinery for a speculative or very unlikely edge case, explain the failure scenario, evidence for its likelihood and impact, simpler alternatives, and estimated code and maintenance cost; obtain the user's approval before expanding scope. Do not use this rule to omit necessary input validation, standard security controls, or requirements already authorized.
- Validate and normalize external data at the boundary, then pass explicit, stable types and established invariants through internal code. Avoid repeating the same checks at every layer. Revalidate at a new trust boundary or when mutation, callbacks, external state, or another documented condition can invalidate an earlier check; make that reason clear.
- Prefer straightforward local code for one-off logic. Extract a helper when it is reused, names a meaningful operation, isolates a genuinely complex section, or materially improves readability or testing. Avoid both unnecessary indirection and oversized functions that mix responsibilities.
- Catch exceptions when there is a specific recovery action, useful domain-level translation, required cleanup, or a need to preserve diagnostic evidence before propagating failure. Otherwise let errors propagate. Prefer scoped resource management and `finally` for cleanup; do not swallow failures or add catch-and-rethrow blocks without value.
- Keep a cohesive operation together when that makes its flow easy to follow. Split it when distinct responsibilities, nesting, or complexity make the code harder to understand or change. Optimize for clear behavior and maintenance, rather than a fixed function count or line limit.

- Check intentional CRLF source/data with `git -c core.whitespace=trailing-space,space-before-tab,cr-at-eol diff --check`. Keep trailing-space checks; do not normalize frozen data or a reviewed dependency merely to satisfy the default newline check. Author new files with explicit UTF-8/newline policy and distinguish raw evidence hashes from canonical-LF source hashes.
